FFmpeg + OpenH264/x264/SVT-AV1/x265 on WASM, on DCP

Drop a video. Watch it transcode locally vs. a real DCP worker fleet, live, into a real 1080p/720p/480p/240p ABR ladder. Real AV1 and HEVC renditions ride alongside H.264, so you can watch each cost more compute per encode and land noticeably smaller. Optional real-decode passes along the way: EBU R128 loudness normalization, multi-audio-track passthrough, and HDR10 color-metadata passthrough.

Proof-of-concept, not a production pipeline

This demonstrates the mechanism - real FFmpeg encoders compiled to WebAssembly, dispatched as chunked DCP work units - not a production-ready service. A production build would differ in real ways:

  • Server-side dispatch. This page is both the job deployer and one racer (in-browser wasm) - convenient for a live demo, not the production shape. A server-side orchestrator could dispatch instead, and each encoder could then run its own multi-threaded build rather than the single-threaded wasm every encoder here uses (no real OS threads available in WebAssembly here, by design).
  • Data off the scheduler. This demo ships every chunk's raw bytes as bound compute.for() arguments, so they transit the scheduler both to workers and back as results. DCP's remote data (RemoteDataSet, job.setResultStorage()) lets workers fetch input from a URL and push results to one instead, so the real bytes never transit DCP's infrastructure at all - meaningful for large media files, and for keeping data on a private network instead of routing it through a public scheduler.

Concrete constraints of this demo build: single video track only (no multi-angle, no subtitles/captions); containers limited to MP4/MOV, MKV, MPEG-TS, and WAV; video decodable as H.264, HEVC, or AV1, audio as AAC or PCM only; up to 8 audio tracks; HDR10 passthrough only (no Dolby Vision - needs a licensed SDK this project doesn't have); and libopenh264 itself hard-caps at 4096×2304 (DCI 4K, 9,437,184px) - this demo's own renditions top out at 1920×1080 (2,073,600px), well under that, but it would matter at true 4K+ output. Documented scope, not a bug list.

AWS MediaConvert-equivalent rates: real published on-demand rates, first pricing tier, resolution-aware SD/HD rate per rendition (simplified, not a full quote)

This number is not derived from running anything on AWS, or from this demo's own encode time. AWS bills MediaConvert per minute of output video duration (a 45-second output bills as 0.75 minutes), not per minute of processing time - so this multiplies each chunk's real duration by AWS's published rate, the same quantity AWS itself bills on, regardless of the hardware underneath. AWS doesn't publicly disclose that hardware (CPU/GPU/custom silicon) - it's an intentionally opaque managed service - which is exactly why a duration-based rate-card comparison is fair here: whatever AWS's hardware costs them is already priced into the published rate. Rates from aws.amazon.com/mediaconvert/pricing/, AWS's own SD/HD split (SD <720p, HD 720-1080p): H.264 uses the Basic tier, $0.0075/min at SD or $0.015/min at HD (this ladder's 1080p/720p rungs). AV1 and HEVC (bake-off comparison only, always 240p/SD) both need the Professional tier at $0.0120/min base × a 3.5x multiplier for AV1 ($0.042/min) or 2x for HEVC ($0.024/min).

DCP prices compute at 1.000 ⊇ (one DCP credit) = $0.0003171 USD per 100 vCPU-seconds. "Raw DCP cost" is priced from each slice's own real compute time, reflecting whatever hardware actually ran it - Bell's internal fleet runs at roughly 38% the per-core speed of AWS's, so real vCPU-seconds can cost proportionally more than a same-hardware comparison would suggest. Run internally, Bell earns back 80% of its compute spend, netting 20% of the raw cost. Resold externally, Bell keeps 80% as revenue and Distributive keeps the other 20%.

Same resolution, three encoders: H.264 vs. AV1 vs. HEVC

Three extra renditions ride along in every job, outside the ABR ladder above: 426×240 (matching the ladder's bottom rung) via libopenh264, libsvtav1, and libx265, each in its own encoder's quality mode (not a bitrate cap, which would make all three converge to the same size regardless of efficiency). AV1 and HEVC both cost meaningfully more compute per encode than H.264. None of the three are in the playback below - comparison only, not delivery: AV1 hits a real ffmpeg muxer warning in MPEG-TS ("muxed as a private data stream"); HEVC muxes cleanly but is excluded anyway since browser HEVC decode support (via MSE) still varies by platform.

5. Playback

This plays the real ABR ladder from section 1's job (1080p/720p/480p/240p, H.264) as one adaptive stream - not a single fixed output. The AV1/HEVC/quality-mode renditions from section 4 are comparison-only and aren't part of this ladder (see that section's note on why).

Writes one complete video per rendition (the ABR ladder above, plus the AV1/HEVC/quality-mode comparison renditions from section 4) into <run-timestamp>/<input-name>-<rendition>.ts, under a folder you pick - stitched from that rendition's chunks in order. Needs the File System Access API (Chrome/Edge).
